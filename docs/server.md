# OHI — сервер мониторinga СМИ (`server/`)

Фоновый Python-процесс (не веб-сервер, без HTTP-эндпоинтов): непрерывно
опрашивает список новостных источников, ищет в новых публикациях заданные
"поисковые образы" (темы с ключевыми словами), переводит найденные новости
на три языка (ru/en/he), сохраняет их в БД и в облачное хранилище, и
уведомляет о находках в Telegram. Часть монорепозитория `D:\demidov_sun\OHI`
(рядом — `web/`, панель просмотра/управления, и `shared/` — общий код).

Точка входа — `server/main_ohi_server.py`. Деплой — Docker-контейнер (ghcr.io,
`server/Dockerfile`, `.github/workflows/deploy-server.yml`).

## Архитектура

- **Многопоточная модель**: каждый источник новостей и каждая вспомогательная
  задача — отдельный `threading.Thread` (daemon), унаследованный от общего
  базового класса **`trafaret_thread.TrafaretThread`** (`trafaret_thread.py`).
  Базовый класс реализует:
  - периодический цикл `run()` — раз в ~60 сек проверяет, не подошло ли время
    следующего запуска (`next_time`), и если да — вызывает переопределяемый
    `work()`;
  - подгрузку и отслеживание изменений своих параметров конфигурации из БД
    (`load_config_params`/`get_difference_config_params`) — период опроса,
    активность и т.п. можно менять "на лету" через веб-страницу "Параметры
    сервисов" (`web/functions.py`), без перезапуска сервера;
  - единообразное логирование старта, изменения параметров, планируемого
    следующего запуска (`sleep`), ошибок (с автоматическим повтором через
    `wait_for_error`, по умолчанию 10 минут).
- **Главный цикл** (`main_ohi_server.py`) не выполняет работу сам — он
  периодически (раз в 30 сек) перечитывает из БД список активных
  RSS/сайтов-источников (`load_list_rss`) и для каждого нового источника
  создаёт и запускает подходящий поток-парсер (по полю `type_rss`). Первый
  запуск каждого потока разнесён по времени (`RSS_JITTER_STEP`), чтобы не
  создавать пиковую нагрузку при старте. Раз в 10 минут проверяется
  работоспособность всех потоков (`check_work`) и в лог пишется общая сводка
  (активных/ошибочных потоков).
- **Данные не хранятся локально** — БД доступна только через REST API
  (`common.send_rest`, тот же бэкенд, что использует и `web/`), полные тексты
  статей — в Google Cloud Storage (`cloud.py`, бакет `llm_news`).
- Обработка сигнала `SIGTERM` (Docker/оркестратор) и `KeyboardInterrupt`
  логирует причину и время работы перед остановкой (`log_shutdown`).

## Потоки-источники новостей (по `rss_list.type_rss`)

| `type_rss`  | Модуль                  | Источник                                           |
|-------------|--------------------------|-----------------------------------------------------|
| `rss`       | `rss_search.py` (`SearchRSS`)      | Произвольная RSS-лента (`xml.etree`)      |
| `tv9co_il`  | `tv9co_il.py` (`TV9coIl`)          | Сайт 9-го ТВ канала Израиля (скрейпинг HTML) |
| `worldnews` | `rss_wordnews.py` (`WordNewsRSS`)  | WorldNews API (топ-новости по странам)    |
| `kremlin_ru`| `kremlin_ru.py` (`KremlinRu`)      | kremlin.ru (скрейпинг HTML)               |
| `WordPress` | `word_press_parser.py` (`WordPressParser`) | Произвольный сайт на WordPress (с пагинацией) |

Общая логика у всех пяти одинаковая: получить список свежих новостей →
проверить каждую на совпадение с активными "поисковыми образами" (темами,
заданными на странице "Поисковые образы" веб-приложения — набор ключевых
слов/фраз, `common.make_search`/`seek`/`seek_article`) → для совпавших:
перевести заголовок/описание на три языка (`translate.py`), при
необходимости дозагрузить полный текст статьи по URL, записать новость в БД
(`common.write_history`) и полный текст — в облако (`cloud.py`) → отправить
уведомление в Telegram-канал (`common.make_tg` + `send_tg`, ссылка на
новость ведёт на `/one_new/<id>/` веб-приложения — открывает её модально на
странице "Новости").

## Вспомогательные потоки

- **`rss_translate.py` (`TranslateRSS`)** — донабирает перевод для новостей,
  у которых он ещё отсутствует: загружает исходный текст из облака,
  переводит на ru/en/he, записывает обратно.
- **`rss_complete.py` (`CompleteRSS`)** — донабирает полный текст статьи для
  новостей без него (`file IS NULL`): скачивает по URL (см. "Извлечение
  текста статьи" ниже), переводит, сохраняет в облако.
- **`clear_logs.py` (`ClearLogs`)** — раз в сутки (по умолчанию) удаляет из
  журнала (`logs` в БД) записи старше `count_days` (по умолчанию 7) дней.

Все три запускаются из `main_ohi_server.py` с разносом по времени (60 сек
между стартами), не зависят от списка RSS-источников.

## Извлечение и перевод текста

- **`article_parser.py` (в `web/`, не в `server/`)** — упомянут отдельно:
  это лёгкий эвристический парсер (JSON-LD/DOM), используемый веб-страницей
  "Новость" для ручного перечитывания статьи; в `server/` для полнотекстовой
  загрузки используется более тяжёлый стек:
  - **`grab_article.py`** — извлечение текста и главного изображения
    (JSON-LD `articleBody`/`image`) с защитой от блокировок; поддерживает и
    CLI-режим (по одному URL или списком из файла).
  - **`hill_article.py`** — извлечение текста и картинки для ОДНОГО URL с
    усиленной защитой от 403: httpx → AMP-варианты → `curl_cffi`
    (имитация браузера) → `trafilatura` как резерв; парсинг — JSON-LD →
    Trafilatura → Readability.
  - Оба — тяжёлые зависимости (NLTK/trafilatura/playwright), импортируются
    лениво (внутри функций), чтобы не грузить память при старте сервера,
    когда полнотекстовая загрузка ещё не нужна.
- **`translate.py`** и **`TranslateManager.py`** — перевод через
  `deep_translator.GoogleTranslator` (неофициальный, без API-ключа).
  `TranslateManager.py` содержит защиту `_is_google_error_page`: Google
  иногда вместо перевода отдаёт свою типовую HTML-страницу ошибки
  ("That's an error... That's all we know"), а `deep_translator` не считает
  это исключением и молча возвращает текст этой страницы как "перевод" —
  проверка по характерным маркерам отсекает такой результат, чтобы он не
  попал в БД (тот же класс защиты, что и `_looks_like_refusal` для
  ChatGPT-переводов на стороне `web/`).
- Домены троттлятся между последовательными запросами
  (`ARTICLE_DOMAIN_DELAY`), чтобы не словить временную блокировку (429/бан)
  от одного и того же сайта.

## Общие модули

- **`common.py`** — REST-клиент к бэкенду (`send_rest`, `login_admin` с
  кешем токена), логирование (`write_log_db`, единый журнал с `web/`),
  работа с конфигурацией потоков (`load_config_params`,
  `get_value_config_param`, `set_value_config_param`,
  `get_difference_config_params` — сравнение старых/новых параметров для
  лога), поиск по ключевым словам (`make_search`, `seek`, `seek_article`),
  создание/поиск тем (`make_theme`, `get_name_theme`), запись найденной
  новости в БД (`write_history`, `is_exist_object`, `fix_new`), работа с
  датами/часовыми поясами, отправка в Telegram (`send_tg`, `make_tg`).
  Часть функций (`decode`/`encode`/`str1000`/`get_duration`) вынесена в
  `shared/ohi_shared/text_utils.py` — общий с `web/common.py` код.
- **`cloud.py`** — Google Cloud Storage (бакет `llm_news`): сохранение и
  загрузка текстов статей, фильтрация "мусорных" строк (виджеты подписки,
  "Нашли ошибку?" и т.п.), которые парсеры иногда захватывают как текст.
- **`config.py`** — переменные окружения (`.env`/`--env-file`): URL REST API,
  схема БД, язык по умолчанию, учётные данные Google Cloud.

## Модули вне основного цикла

- **`doc_text.py`**, **`doc_translate.py`** — работа с DOCX/PDF-документами
  и отдельным бакетом (`liberman-transcriptions`): конвертация PDF→DOCX
  (`pdf2docx`), перевод через Google Translate. Не импортируются и не
  запускаются из `main_ohi_server.py` — самостоятельный/невключённый в
  текущий главный цикл функционал (класс `DocTranslate` в `doc_translate.py`
  тоже унаследован от `TrafaretThread`, но нигде не инстанцируется).

## Логирование

Общий с `web/` журнал (`common.write_log_db`, таблица `logs` в БД,
просматривается на странице "Лог работы"). Каждый поток при старте пишет
`✈LOAD`, при каждом цикле — либо `🕒sleep` (успех, время следующего запуска),
либо `❌ Exception` (ошибка, повтор через `wait_for_error`). Главный процесс
пишет `🔥Startup`/`🛑Shutdown` и периодическую сводку `info` (`check_work`,
раз в 10 минут: сколько потоков активно/в ошибке).
